# Retranslator Engine Reference

Retranslator is a proprietary, fully offline-capable multilingual translator spanning two Gradle modules: `:app` (phone/foldable/tablet — Translate/Conversations/Practice/Learn tabs, originally built for a Retroid Pocket 2+, Unisoc T310, Android 9/API 28, arm64-v8a) and `:wear` (Samsung Galaxy Watch6 Classic standalone, SM-R965U, Exynos W930, armeabi-v7a-only, ~1.8GB RAM). This document indexes every engine across both modules — translation, speech-to-text, text-to-speech, vision/OCR, supporting infrastructure, and the Learn content engine — with real capacity numbers, mechanism, and disclosed gaps, each grounded in a specific file and line range. It supersedes no spec doc; `docs/specs/fold5-adaptation.md`, `docs/specs/galaxy-tab-s9fe-adaptation.md`, and `docs/specs/watch6-classic-adaptation.md` remain the chronological build/verification record. This is a standing reference, current as of 2026-08-16.

Module tags: **(app)** = `:app` only, **(wear)** = `:wear` only, **(both)** = present in both modules (usually as independent, near-duplicate implementations — see the recurring "no shared `:core` module" gap below).

## 1. Translation engines

| Engine | Module | Real coverage | Mechanism |
|---|---|---|---|
| ML Kit Translate (NMT) | both | 59 on-device languages, one model per language | `TranslatorOptions` + `Translation.getClient()`, bilingual-with-English pivot |
| ML Kit Language Identification | app | ~110-language model, single top-guess consumed | `LanguageIdentification.getClient()`, default 0.5 confidence threshold |

### ML Kit Translate (Neural Machine Translation) — both
- **Library/version**: `com.google.mlkit:translate:17.0.3`, pinned identically in `app/build.gradle.kts:90` and `wear/build.gradle.kts:125` (deliberately kept in lockstep per that file's own comment). Classes: `com.google.mlkit.nl.translate.{Translation, Translator, TranslatorOptions, TranslateRemoteModel}`; download/inventory via `com.google.mlkit.common.model.{RemoteModelManager, DownloadConditions}`.
- **Real capacity**: 59 on-device-downloadable languages, one model per language (not per pair) — confirmed via `TranslateLanguage.getAllLanguages()`, cross-checked against `docs/specs/galaxy-tab-s9fe-adaptation.md`'s live PackInventory ("92 total: 59 translation + 25 Vosk + 8 Piper", verified on-device via the Manage Packs summary card reading "X of 92"). No static list exists in-repo to grep — `LanguageCatalog.codes` enumerates it live from the ML Kit AAR's bundled catalog.
- **How it works**: `app/src/main/java/com/retroid/translator/engine/TranslationEngine.kt` and `wear/src/main/java/com/retroid/translator/wear/engine/TranslationEngine.kt` are a byte-for-byte port of each other (package name is the only diff; wear's own doc comment says so). Both expose `isModelDownloaded(code)`, `downloadModel(code, requireWifi)`, `deleteModel(code)` (app-only, Manage Packs), and `translate(context, sourceCode, targetCode, text)`, which now pre-flights a `getDownloadedModels()` check (both codes, one round trip — the same `srcOk`/`tgtOk` pattern `TranslateFragment.refreshModelStatus` uses) and a `DownloadManager.isOnWifi(context)` check before ever building `TranslatorOptions`/calling `downloadModelIfNeeded(DownloadConditions)` (see fixed gap #1 below for the full history). `RemoteModelManager.getDownloadedModels()` is queried once per status check (both source AND target independently), not once per language, avoiding ~59 separate async round-trips. ML Kit's translate models are bilingual-with-English; a non-English-to-non-English pair pivots through two on-device models under the hood — why the UI always checks/downloads BOTH codes separately even for one displayed pair.
- **Known limits/gaps**:
  1. **~~Wi-Fi gating is inconsistent by call path.~~ FIXED (2026-08-16, branch `translate-wifi-gating`).** Previously, the app's explicit UI download buttons — `TranslateFragment.downloadTranslateModels()` and `BulkDownloadCoordinator.kt` — called `downloadModel(code, requireWifi=true)`, but `translate()` itself (the path exercised on every Translate tap, including first use before any explicit download) called the bare, no-argument `translator.downloadModelIfNeeded()`, applying ML Kit's unrestricted default and letting a first-use Translate tap silently trigger a cellular download.
     Fix: confirmed via `javap` against the real `com.google.mlkit:translate` AAR's `Translator.class` that `downloadModelIfNeeded(DownloadConditions)` is a genuine public overload (both `downloadModelIfNeeded()` and `downloadModelIfNeeded(DownloadConditions)` are declared), so `translate()` (`TranslationEngine.kt:88-108` app / `:38-56` wear) now always builds `requireWifi()` conditions before calling it — matching the explicit Download buttons. Because the actual enforcement of an unmet `DownloadConditions` constraint lives in the closed-source Play services layer (not the client jar), the fix does not depend on guessing whether that produces a fast failure or an indefinite pend; instead `translate()` pre-flights (`attemptTranslate`, `TranslationEngine.kt:110-149` app / `:60-97` wear): if both language models are already downloaded, it proceeds regardless of network state (preserves the "offline forever after download" promise); if either model is missing and the device isn't on Wi-Fi right now, it never touches the network at all and calls `onError` with a clear message ("Translation pack not downloaded yet. Connect to Wi-Fi, then translate again to download it...") that flows through every call site's existing error handling. All 12 real call sites across both modules were updated to pass a `Context` — `TranslateFragment.kt` (5: `translateWith`, `translateDirectional`, `translateAndSpeakContinuous`, `translateForTranscript`, `broadcastToRoster`), `ConversationsFragment.kt` (2), `wear/TranslateController.kt` (1), plus 3 pre-existing debug-harness call sites (`ContinuousFlowProtoActivity.kt`, `OcrTestActivity.kt`) that also compile against the new signature.
     Verification: `./gradlew clean :app:assembleDebug :wear:assembleDebug` — both succeed (confirms the real, network-resolved `17.0.3` dependency accepts the same overload the local `17.0.2` cache/`javap` showed). Real on-device run, Galaxy Z Fold 5 (RFCW80CK2RW), via a throwaway debug harness (`app/.../prototype/WifiGateTestActivity.kt`, same pattern as `OcrTestActivity`/`ContinuousFlowProtoActivity`, exercising the real production `TranslationEngine.translate()` — not a mock): with Wi-Fi OFF (`adb shell svc wifi disable`, confirmed via `dumpsys wifi`) and an undownloaded pair (`mt`→`ka`), `translate()` short-circuited in **53ms** with the new clear message and no network attempt (logcat tag `WifiGateTest`); an already-downloaded pair (`ga`→`en`) translated successfully in **378ms** with Wi-Fi still off, confirming the offline-after-download promise is unregressed. With Wi-Fi back ON, an undownloaded pair (`cy`→`ga`) auto-downloaded and translated in 12765ms ("Dia duit"), confirming auto-download-on-Wi-Fi is unchanged. A real UI pass (typed "hello" into the actual Translate tab, en→es, both already downloaded) returned "hola" — screenshotted, confirming the normal manual-flow translate path is unregressed end-to-end through the real UI, not just the harness.
  2. **No formality/register control** — `TranslatorOptions` exposes only `setSourceLanguage`/`setTargetLanguage`; ML Kit Translate's public API has no formality parameter at all (library-level fact, not an app gap).
  3. `docs/specs/watch6-classic-adaptation.md` §5 flags `translate()` as never verified end-to-end on real Watch6 Classic hardware as of that doc ("triggers a real ~30MB model download via Play services") — still true; this pass's wear verification was code review + compile only (no watch hardware in this pass's `adb devices -l`), not a real Watch6 Classic run.

  5. `WearLanguages.kt` curates only 12 of the 59 languages (en/es/fr/de/zh/ja/ko/ar/pt/it/ru/hi) — a deliberate scoping decision (file header + watch6 spec §6), not a bug.

### ML Kit Language Identification (auto-detect source language) — app
- **Library/version**: `com.google.mlkit:language-id:17.0.5` (`app/build.gradle.kts:91`). Absent from `:wear` entirely — grep across `wear/build.gradle.kts` and every `wear/*.kt` for `language-id`/`LanguageIdentification`/`identifyLanguage` returns zero hits. Watch's 12-language chip cycles fixed pairs manually (`watch6-classic-adaptation.md` §11 item 7, §6).
- **Real capacity**: Same underlying ML Kit langid model (~110 languages, Google's published catalog) but only ever fed text from the 59-language Translate catalog, consuming only the single top-guess code (or sentinel `"und"`) — no confidence score, no ranked alternatives, no custom threshold read or used anywhere.
- **How it works**: Lazily instantiated once as a fragment field, `LanguageIdentification.getClient()` (`TranslateFragment.kt:254`) — the default client; no `LanguageIdentificationOptions` builder call anywhere in the repo, so ML Kit's default 0.5 confidence threshold applies unmodified. Wired to exactly one control across the Translate tab's 8 layout variants: the auto-detect checkbox, present on 2 of 8 (`DEFAULT`'s `checkboxAutoDetect`, `FLEX_DEFAULT`'s `checkboxFlexAutoDetect`, both toggling the same shared `autoDetectEnabled` field). When enabled, `performTranslate()` calls `languageIdentifier.identifyLanguage(text)` instead of the manual source spinner; `"und"` shows a toast asking for manual pick, otherwise the detected code feeds `TranslationEngine.translate()` directly. The identify-then-translate pattern is duplicated verbatim at `TranslateFragment.kt:622-633` and `:1472-1473` — unlike translate/mic/speak, no shared helper was factored out for this branch.
- **Known limits/gaps**: Only 2 of 8 Translate layouts expose auto-detect at all; the other 6 (single_circle, live_transcript, face_to_face, across_table, multi_broadcast, mirror_panes) leave `autoDetectEnabled` at whatever it was last set to with no UI to change it. Not ported to `:wear` — not a missing feature relative to a plan, since the watch's fixed chip-cycling UI is a structurally different, manual-only design. No confidence score surfaced to the user. No spec doc discusses ML Kit Language-ID's real accuracy — no on-device verification evidence (screenshots/logcat) exists for the auto-detect path anywhere, unlike Translate/Vosk/Camera-OCR.
- **Source**: `TranslateFragment.kt:35-38,254,619-638,872-879,1472-1473,1542-1545`; `app/build.gradle.kts:91`; `wear/build.gradle.kts` (absence confirmed).

## 2. Speech-to-text (STT)

| Engine | Module | Real coverage | Mechanism |
|---|---|---|---|
| Vosk offline STT | both | 25 languages (app) / 12 curated (wear) | Kaldi small-model dir, one resident `Model` per `VoskEngine` |
| MicPipeline audio capture | both | tap-to-talk (app-only) + continuous/VAD (both) | Raw `AudioRecord` 16kHz PCM16, in-house adaptive-RMS VAD |
| Dual-recognizer auto-detect | app | 2 simultaneously-resident models, real-speech 3/6 | Two parallel `Recognizer`s raced on mean word-confidence |
| Wear single-recognizer listening | wear | 1 recognizer, one-directional | No race — source language pre-known from picker |

### Vosk offline STT engine (VoskEngine) — both
- **Library/version**: `com.alphacephei:vosk-android:0.3.75` + `net.java.dev.jna:jna:5.18.1@aar`, pinned identically in `app/build.gradle.kts:140-141` and `wear/build.gradle.kts:136-137`. JNA's `libjnidispatch.so` loads via Android's ClassLoader native-lib path (`nativeloader:` logcat line); Vosk's own `libvosk.so` is loaded by JNA's own dlopen mechanism and produces **no** `nativeloader:` line (directly compared, `watch6-classic-adaptation.md` §2). Model format: Kaldi small-model directory tree (`conf/` + `am/`), not a single file — `VoskEngine.effectiveModelPath()` (`VoskEngine.kt:39-46`) unzips-then-searches one directory level deep for either marker.
- **Real capacity**: Phone catalog (`VoskModelCatalog.kt:20-46`): exactly 25 languages — en, es, fr, de, it, pt, ru, nl, zh, ja, ko, hi, tr, pl, cs, ca, fa, uk, vi, ar, eo, gu, te, sv, kk. Real per-model sizes span 31MB (Portuguese) to 289MB (Swedish) — README's "~40–140MB each" undercounts both ends. Wear catalog (`WearLanguages.kt:47-59`): hand-curated 12 of the 25, 31–100MB each, ~597MB if all 12 downloaded — flagged as a real, unresolved storage question against the watch's ~4.7GB free space.
- **How it works**: Single-resident-model design on both modules — one `VoskEngine` holds at most one loaded `org.vosk.Model`; switching language unloads the previous (`Model.close()`) before loading the next (`loadModelAsync`, `VoskEngine.kt:50-75`). `Recognizer` objects are cheap per-utterance children of the resident `Model` (`newRecognizer()`, `VoskEngine.kt:78-86`) — the model, not the recognizer, is the expensive resident object. Conversations' dual-language auto-detect gets two simultaneously-resident models "for free" via the caller (`ContinuousConversationController`) simply holding two independent `VoskEngine` instances, each unaware of the other. Measured cost: ~214MB native-heap delta / ~330MB total process PSS with English+Spanish small models resident on a Galaxy Z Fold 5 (11.4GB RAM) — comfortable headroom. The wear port is a near-identical Kotlin copy requiring zero logic changes — only `ndk.abiFilters` differ — plus one addition: `probeNativeLoad()`, a diagnostic that constructs a `Model` against a guaranteed-missing path to prove native/JNI loads on a new ABI without a real model (classifies `CLEAN_MANAGED_REJECTION` / `NATIVE_LOAD_FAILED` / `UNEXPECTED_SUCCESS`).
- **Known limits/gaps**: Single-resident-model is a harder constraint on wear — the real Watch6 Classic has ~1.8GB total RAM and is armeabi-v7a-only with **no 64-bit ABI at all**, invalidating the original "reuse the phone's arm64-v8a build" assumption. Both modules duplicate `VoskEngine`/`MicPipeline`/`VoskResultParsing` as near-identical hand-copies, disclosed as recommended (not done) follow-up in both specs. As of the wake-lock verification pass (`watch6-classic-adaptation.md` §13, 2026-08-16), Spanish and French Vosk models are downloaded on the real watch and a real `Recognizer` chain was confirmed to run end-to-end for ambient-noise VAD triggers (surfaced as "Didn't catch that — listening...") — but **no deliberately spoken phrase has ever been decoded on real wear hardware**; only the native-load mechanism and the empty-result pipeline path are proven.
- **Source**: `app/.../engine/VoskEngine.kt:14-125`; `app/.../engine/VoskModelCatalog.kt:1-53`; `app/build.gradle.kts:138-141`; `wear/.../engine/VoskEngine.kt:14-167`; `wear/.../engine/WearLanguages.kt:1-63`; `wear/build.gradle.kts:127-137`; `fold5-adaptation.md` §4 (lines 84-93); `watch6-classic-adaptation.md` §2 (lines 68-99) and Goal table (lines 9-20).

### MicPipeline audio capture (tap-to-talk vs. continuous/VAD) — both
- **Library/version**: No third-party audio library — raw `android.media.AudioRecord` (16kHz mono PCM16, `AudioRecord.getMinBufferSize(...).coerceAtLeast(4096)` → 4096 bytes/chunk on tested devices). In-house adaptive-RMS VAD, not an ML VAD model, deliberately (`MicPipeline.kt:217-220`).
- **Real capacity**: One phone class implements BOTH capture modes; the wear port implements ONLY continuous/VAD — tap-to-talk (`start()`) was deliberately not ported, per the watch's "auto-listening like Shazam, not tap-to-talk" decision. Identical VAD tuning constants on both: `MIN_ABSOLUTE_FLOOR=80.0`, `TRIGGER_MULTIPLIER=4.0`, `NOISE_FLOOR_EMA_ALPHA=0.05`, `VAD_PREROLL_CHUNKS=2`, `speechTriggerChunks=2`, `silenceTimeoutMs=900`, `maxUtteranceMs=12000` (`MicPipeline.kt:239-244,406-409`; wear `MicPipeline.kt:50-55,192-195`), derived from real measurement: bundled `real_speech_corpus` clips show near-silent studio floor RMS ~1-5 jumping >100x to RMS 300-4800 at speech onset.
- **How it works**: Tap-to-talk (`MicPipeline.start()`, phone-only, `MicPipeline.kt:80-199`) opens one `AudioRecord` for the call's duration, feeds every chunk to ONE caller-supplied `Recognizer` via blocking `acceptWaveForm()` directly on the capture thread, stopping on first `isFinal=true` non-blank result or after `maxDurationMs` (default 15s) of silence — used by Translate's mic button, Practice recordings, Conversations' original turn-taking flow. Continuous/VAD listening (`startContinuousListening()`, `MicPipeline.kt:239-365`, wear `MicPipeline.kt:50-166`) is recognizer-agnostic — never owns a `Recognizer`, only hands raw PCM to the caller via `onAudioChunk()` (one recognizer on wear, two in parallel for Conversations). State machine (IDLE/SPEECH): IDLE tracks an exponentially-adapting noise floor (alpha=0.05) buffering into a pre-roll ring; once RMS clears `max(80.0, noiseFloor*4.0)` for 2 consecutive chunks, fires `onSpeechStart()`, replays the pre-roll, switches to SPEECH, streams until 900ms silence or a 12s ceiling fires `onSpeechEnd()` and auto-returns to IDLE.
- **Known limits/gaps**: The VAD's RMS-jump derivation is from clean studio-recorded clips (OpenSLR SLR83/SLR72) — never validated against live room ambient noise or a genuinely worn/outdoor watch mic (no live human speaker available to any agent in this environment; disclosed in both the class doc and both specs). Continuous listening depends on a wake-lock + `FOREGROUND_SERVICE_TYPE_MICROPHONE` foreground service (`ContinuousListeningService`) to survive a screen lock — without it, continuous listening silently dies at screen-lock (Android Doze/OEM battery management + Android 14's mic-capture-while-backgrounded requirement); a real bug found/fixed for Conversations (4.5-5m44s backgrounded, real-verified) and again for Translate's `single_circle` widget, and separately ported to wear (7m40s screen-off, real-verified).
- **Source**: `app/.../audio/MicPipeline.kt:14-411`; `wear/.../audio/MicPipeline.kt:11-197`; `fold5-adaptation.md` §4 (lines 168,174-222); `watch6-classic-adaptation.md` §3 (101-107), §13 (220-269).

### Dual-recognizer auto-detect (ContinuousConversationController) — app
- **Library/version**: No new library — pure Kotlin orchestration over two `org.vosk.Recognizer` instances (from two independent `VoskEngine` instances) plus `VoskResultParsing.kt`'s shared parsing helpers.
- **Real capacity**: Prototyped/measured on a real Galaxy Z Fold 5 (RFCW80CK2RW, Snapdragon 8 Gen 2). Synthetic eSpeak-TTS accuracy: **12/12** correct (6 English+Spanish sentences × 2 runs). Real recorded human speech (OpenSLR SLR83 UK/Irish English + SLR72 Colombian Spanish, CC BY-SA 4.0): **3/6** correct — a real, measured drop. Concurrent-decode cost: ~1.9-2.03x a single recognizer's solo wall time (837.7/834.7ms dual vs 445.5/423.8ms solo per run), RTF topped out ~0.60. Two resident small models: ~214MB extra native heap / ~330MB total PSS on Fold 5's 11.4GB RAM.
- **How it works**: Because Conversations is always a fixed two-language pair (not open-set language-ID), the app runs BOTH languages' recognizers in parallel on the identical audio-chunk stream and picks whichever has higher mean per-word confidence, rather than true spoken-language ID (which Vosk's monolingual-per-model design can't do pre-transcription). `handleSpeechStart()` builds two fresh `Recognizer`s (`setWords(true)` for per-word `conf`), one worker thread per recognizer draining its own `BlockingQueue` fed by `handleAudioChunk()` sharing the same `ByteArray` chunk (read-only, safe). `handleSpeechEnd()` detaches queues immediately, joins both threads, calls `VoskResultParsing.pickLanguage()` on the two `finalResult()` JSONs: primary signal mean `avgWordConf`; if either JSON lacks `conf`, falls back to raw word count. A separate "early guess" heuristic surfaces provisional mid-utterance UI feedback but never drives the actual translate/speak decision.
- **Known limits/gaps**: The 3/6 real-speech drop has a diagnosed failure mode: 2 of 6 clips produced completely empty transcription from BOTH recognizers (total STT miss, not a wrong-language pick); a 3rd had the correct-language recognizer return empty while the wrong-language recognizer hallucinated a phonetically plausible false transcription, and because the correct side had no `conf` field the decision fell to word-count fallback, which the wrong side won by producing anything at all — reproduced identically across two independent harnesses. Real Fold 5 hardware never ran this measurement (Retroid Pocket 2+ substitute for latency; accuracy figures are hardware-independent). Tap-to-fix reassign affordance exists as the built, real-device-verified safety net for wrong picks.
- **Source**: `app/.../conversation/ContinuousConversationController.kt:1-343` (doc 13-53, handlers 125-234); `app/.../engine/VoskResultParsing.kt:33-68`; `fold5-adaptation.md` §4 (77-172).

### Wear single-recognizer continuous listening (TranslateController) — wear
- **Library/version**: Same `org.vosk.Recognizer`/`VoskEngine` (0.3.75), but only ONE recognizer per session — no parallel-race machinery. Uses a trimmed `VoskResultParsing.kt` (text/partial extraction only; `avgWordConf`/`pickLanguage` deliberately not ported).
- **Real capacity**: Native-stack load proven on the real SM-R965U: `probeNativeLoad()` returned `CLEAN_MANAGED_REJECTION` (libvosk.so loaded, JNI initialized, Kaldi cleanly threw `IOException` on a missing model path) with the process staying alive. Idle app PSS ~78.9MB with zero model loaded, against ~426MB real measured `MemAvailable`. By the wake-lock pass (§13, 2026-08-16), French and Spanish Vosk models were downloaded and a real VAD-triggered `Recognizer` chain confirmed to execute during a 7m40s backgrounded interval — but **no deliberately-spoken utterance has been decoded on real wear hardware**; STT decode accuracy is 0 data points on this device.
- **How it works**: `TranslateController` is explicitly NOT a port of `ContinuousConversationController` — one-way flow ("pick source+target, watch listens and translates one way"), source already known from an explicit picker (`cycleSourceLang`/`cycleTargetLang`). Follows the phone's continuous-listening SHAPE without dual-recognizer machinery: `onSpeechStart()` creates exactly one `Recognizer`; `onAudioChunk()` calls `acceptWaveForm()` synchronously on the capture thread (the phone's tap-to-talk blocking pattern, reused since there's only one recognizer); `onSpeechEnd()` finalizes, extracts text, hands off directly to `TranslationEngine.translate()` then `SystemTtsSpeaker.speak()` — no confidence-comparison step exists.
- **Known limits/gaps**: Two compounding reasons this stays single-recognizer: (1) product-shape — one-directional flow, nothing to auto-detect; (2) hardware headroom — ~1.8GB RAM vs. the Fold 5's 11.4GB and 32-bit-only ABI make two resident models proportionally far costlier, though this exact tradeoff was never directly measured on wear. eSpeak/Piper were not ported either — wear falls back to system `TextToSpeech`, an explicit quality downgrade disclosed in the spec.
- **Source**: `wear/.../TranslateController.kt:24-277`; `wear/.../engine/VoskResultParsing.kt:6-28`; `watch6-classic-adaptation.md` §2 (68-99), §11 item 8 (206), §13 items 4-5 (257-258), §9 (179-189).

## 3. Text-to-speech engines

| Engine | Module | Real coverage | Gender support |
|---|---|---|---|
| EspeakEngine | app | 114 bundled dicts, ~100+ voices | Both genders, all languages (structural) |
| PiperTtsEngine | app | 8 voices / 4 languages | All 4 languages have both genders |

### EspeakEngine (eSpeak NG formant synthesis — always-available floor) — app
- **Library/version**: eSpeak NG, GPL-3.0. Bundled directly (not Maven): `jniLibs/arm64-v8a/libttsespeak.so` + `assets/espeak-ng-data`. Driven via the vendored `com.reecedunn.espeak` JNI bridge (`app/.../com/reecedunn/espeak/{SpeechSynthesis,Voice,VoiceVariant,CheckVoiceData}.java`, Apache-2.0, copied from upstream espeak-ng android/ source, kept byte-for-byte except removing one Android-string-resource helper). No upstream espeak-ng version is pinned or recorded anywhere in-repo (checked build.gradle.kts, README, both other specs).
- **Real capacity**: 114 bundled `*_dict` files (`ls *_dict | wc -l` = 114), matching `EspeakLanguageMap.kt`'s doc-comment ("~114 language dictionaries") and README's "100+ voices." `EspeakEngine.initBlocking()` collapses `SpeechSynthesis.getAvailableVoices()` into `voicesByLang: Map<String,Voice>` keyed by `Voice.locale.language` via `associateBy` — multiple country/dialect variants of one language collapse to a single entry; true post-collapse count only known via the (not-captured-this-pass) logged `voices=${voicesByLang.size}` line. Every entry supports both MALE and FEMALE — a structural guarantee (single global `VoiceGender` enum, no per-language carve-out).
- **How it works**: `speak(text, langCode, gender, ...)` maps the ML Kit code through `EspeakLanguageMap.toEspeakLanguage()` (2 real remaps: `zh`→`cmn`, `iw`→`he`; everything else passes through), looks up the `Voice`, converts `gender` via `VoiceVariant.parseVoiceVariant()`. The real mechanism is NOT `+m`/`+f` string-suffix concatenation (as README's prose describes) — for the literal male/female case, `variant.variant == null`, so `SpeechSynthesis.setVoice()` calls `nativeSetVoiceByProperties(voice.name, variant.gender, variant.age)` with `GENDER_MALE=1`/`GENDER_FEMALE=2` int constants, a structured `espeak_SetVoiceByProperties`-style native call; the string-suffix path exists in the same function but is only reached for non-gender named variants (e.g. `klatt`), never for male/female. Synthesis streams PCM via a `SynthReadyCallback` into an `AudioTrack` (`MODE_STREAM`) off-main-thread on a single-thread Executor; `speaking` is a single-flight `AtomicBoolean`.
- **Known limits/gaps**: No pinned upstream version anywhere. `voicesByLang`'s `associateBy` collapse silently reduces any language with multiple locale variants to whichever lands last in iteration — one entry per ISO code, not selectable further. Formant-synthesized audio is explicitly "intelligible but robotic" (README) — the guaranteed-available floor Piper upgrades on top of, not a quality target itself.
- **Source**: `app/.../engine/EspeakEngine.kt` (237 lines); `app/.../com/reecedunn/espeak/SpeechSynthesis.java:170-178,297-317`; `.../VoiceVariant.java:31-43`; `app/.../engine/EspeakLanguageMap.kt`; `app/build.gradle.kts:143-145`; `README.md:16-17`; `ls app/src/main/assets/espeak-ng-data/*_dict | wc -l` = 114.

### PiperTtsEngine (sherpa-onnx neural TTS — natural-voice upgrade tier) — app
- **Library/version**: sherpa-onnx v1.13.4 (Apache-2.0, k2-fsa/sherpa-onnx). No Maven Central artifact — vendored as `app/libs/sherpa-onnx-classes.jar` + `app/src/main/jniLibs/arm64-v8a/lib{onnxruntime,sherpa-onnx-c-api,sherpa-onnx-cxx-api,sherpa-onnx-jni}.so`, hand-extracted from the upstream 1.13.4 AAR for arm64-v8a only. Voice packs distributed as `.tar.bz2` via Apache Commons Compress 1.26.1 (JDK's `java.util.zip` has no bzip2 support). Piper (the upstream training project) relicensed GPL-3.0 in Oct 2025; README documents why this doesn't propagate (sherpa-onnx only reads Piper's `.onnx` weights as data).
- **Real capacity**: Exactly **8 voices** across **4 languages**, matching README's license table: `en_US-ljspeech-medium` (F, public domain), `en_US-joe-medium` (M, CC0), `de_DE-thorsten-medium` (M, CC0), `de_DE-kerstin-low` (F, CC0), `es_ES-davefx-medium` (M, CC0), `es_MX-claude-high` (F, Apache-2.0), `fr_FR-siwis-medium` (F, CC-BY 4.0, attribution required), `fr_FR-gilles-low` (M, CC0). All 4 languages have both genders. Every entry's `approxSizeMiB` is hardcoded to 65 regardless of actual quality tier — a stated approximation. Only one voice resident in native memory at a time (loading a new one calls `releaseTtsLocked()` first).
- **How it works**: `isVoiceDownloaded()`/`effectiveVoiceDir()` do real completeness validation, not just existence checks: `.onnx` model >=10MB (`MIN_MODEL_BYTES`), `tokens.txt` non-empty, all 4 required espeak-ng-data files present — added after a real found-and-fixed bug (commit `ff163ea`, "Fix native crash on loading an incomplete Piper voice pack") where an incomplete extraction caused a native segfault un-catchable by Kotlin try/catch. `loadVoiceAsync()` builds `OfflineTtsConfig(vits=...)` (numThreads=2, provider='cpu'). `speak()` calls `tts.generate(text, sid=0, speed=1.0f)`, synthesizing the whole utterance into memory (unlike eSpeak's streaming callback), writing to an `AudioTrack` (`ENCODING_PCM_FLOAT`). Each call logs real synthMs/audioMs/RTF — `fold5-adaptation.md` cites empirical RTF 0.35–0.63 on the Unisoc T310 (attributed to README though that exact figure isn't in current README text — minor doc-drift, not a fabricated number).
- **Known limits/gaps**: Strictly a per-(language,gender) upgrade layer, not a replacement — Piper's upstream catalog covers only a small subset of languages and rarely both genders per language, so this app's 4-language/8-voice set is a deliberately curated, license-vetted subset. Requires Wi-Fi + ~65MB per voice before usable; falls back silently to eSpeak (via `TtsRouter`) on any failure.
- **Source**: `app/.../engine/PiperTtsEngine.kt` (325 lines); `app/.../engine/PiperVoiceCatalog.kt` (112 lines); `app/build.gradle.kts:147-156`; `README.md:59-70,18`; `fold5-adaptation.md:10,96`; commit `ff163ea`.

### TtsRouter (selection/fallback layer, not a synthesis engine) — app
- **Library/version**: In-house Kotlin, no external dependency — thin dispatcher over `EspeakEngine`/`PiperTtsEngine` (`app/.../engine/TtsRouter.kt`, 132 lines).
- **Real capacity**: Single entry point every screen in `:app` speaks through (Translate/Conversations/Practice/Learn all call `TtsRouter.speak()`, per README's Architecture section). One shared Female/Male preference (SharedPreferences-backed) feeds every call site.
- **How it works**: For a given (langCode, gender): looks up `PiperVoiceCatalog.forLanguageAndGender()`. If a match exists AND `piper.isVoiceDownloaded()` is true, uses Piper — loading via `loadVoiceAsync()` if not already resident (`isReadyFor()` check first). If Piper load or `speak()`'s own `onError` fires, logs `Log.w` and transparently retries the same text through eSpeak — the only visible error path is if eSpeak itself then also fails. No Piper catalog entry, or entry-but-not-downloaded, goes straight to eSpeak without attempting Piper. `activeEngineLabel()` gives the UI a human-readable "what will actually speak this" string.
- **Known limits/gaps**: Fallback is per-call, not sticky — a transient Piper failure degrades that one utterance only; the next call still tries Piper first, since `TtsRouter` holds no failure-memory state.
- **Source**: `app/.../engine/TtsRouter.kt:37-87`; `README.md:18,24`.

### SystemTtsSpeaker (platform TextToSpeech wrapper — :wear's entire TTS surface) — wear
- **Library/version**: `android.speech.tts.TextToSpeech` — stock Android platform TTS, no pinned third-party engine. On the real SM-R965U, confirmed via logcat to bind to `com.samsung.SMT` (Samsung's engine), not necessarily Google's, even though `com.google.android.tts` is also present per `pm list packages`.
- **Real capacity**: Wraps exactly one capability — `speak(text, langCode, onDone, onError)` — **no gender parameter in the method signature at all**, a structural gap versus `:app`'s VoiceGender toggle, not just a quality downgrade. `Locale.forLanguageTag(langCode)` passed to `engine.setLanguage()`; `LANG_MISSING_DATA`/`LANG_NOT_SUPPORTED` only logs a warning and still attempts to speak with the default. TTS engine *connection* confirmed live (real logcat "Sucessfully bound to com.samsung.SMT" / "Connected to TTS engine") but "produces audible speech for a translated sentence" was never confirmed this pass.
- **How it works**: Direct 1:1 wrap of the platform `TextToSpeech` object — no routing, no fallback, no offline voice catalog: this is `:wear`'s entire TTS stack. An `UtteranceProgressListener` is set per-call with a fresh random UUID; `onDone`/`onError` bubble straight to the caller with no retry path (no second engine to fall back to).
- **Known limits/gaps**: Two compounding, real findings for why eSpeak/Piper weren't ported: (1) both are vendored as arm64-v8a-ONLY `.so` files with zero in-repo build recipe for any other ABI; (2) the real device's `ro.product.cpu.abilist` = `armeabi-v7a,armeabi` with an **empty** `abilist64` — confirmed directly via adb on the physical Watch6 Classic — genuinely 32-bit-ARM-only hardware. Whether eSpeak-ng/sherpa-onnx/onnxruntime can even be built for 32-bit ARM from current upstream sources was explicitly not investigated (§9/§12 item 5). A `watch6-native-tts` branch + worktree (`Z:/Dev/RetroidTranslator-watch6-tts`) exist scaffolded for this follow-up, but as of this pass carry **zero commits** beyond their branch point and a clean working tree — created, not started.
- **Source**: `wear/.../tts/SystemTtsSpeaker.kt` (72 lines, doc 10-26); `watch6-classic-adaptation.md` §4 (109-131), Goal table row "CPU ABI" (14), §9/§12 item 5 (179-189,210-217); `wear/build.gradle.kts:139-148`.

### DownloadManager (phone) — app
- **Library/version**: Plain `java.net.HttpURLConnection` + `java.util.zip.ZipInputStream` for `.zip`; Apache Commons Compress (`BZip2CompressorInputStream` + `TarArchiveInputStream`) for `.tar.bz2` — no dedicated HTTP/zip library added.
- **Real capacity**: Two extraction paths — `downloadAndUnzip` (Vosk `.zip`) and `downloadAndExtractTarBz2` (Piper `.tar.bz2`, sherpa-onnx's release format). Both funnel through one private `runDownload`: single-threaded executor (one download at a time, app-wide), 64KB read/write buffer, `connectTimeout=15000ms`, `readTimeout=30000ms`, Wi-Fi-gated by default (`requireWifi=true`, `ConnectivityManager.getNetworkCapabilities().hasTransport(TRANSPORT_WIFI)`), integer percent progress posted to the main-thread `Handler` only when the value changes.
- **How it works**: Wi-Fi gate short-circuits before any network I/O. On pass, downloads to a temp file in `context.cacheDir`, streaming progress by content-length; on completion deletes any pre-existing `destDir`, recreates it, extracts entry-by-entry. Any exception at any stage deletes `destDir` recursively before reporting failure — specifically to prevent a half-written pack from reading as "downloaded" to a naive completeness check.
- **Known limits/gaps**: The destDir-deletion-on-failure behavior fixes a real bug hit during on-device testing (a Piper pack's small files landed before the connection dropped mid-download). Deprecated `TarArchiveInputStream.nextTarEntry` is a known, disclosed, non-blocking compiler warning. Single-threaded executor means bulk downloads are inherently sequential at this layer too, not just at the coordinator layer.
- **Source**: `app/.../engine/DownloadManager.kt:1-188`.

### DownloadManager (wear) — wear
- **Library/version**: Plain `HttpURLConnection` + `ZipInputStream` — identical mechanism to the phone's, no external library.
- **Real capacity**: A trimmed port — only the `.zip` (Vosk) path exists; `.tar.bz2` (Piper) was not ported, since `:wear` doesn't carry Piper/sherpa-onnx. Same Wi-Fi gate, 64KB buffers, single-threaded executor, destDir-wipe-on-failure — inlined into one function, no code sharing with the phone's version.
- **Known limits/gaps**: Explicitly documented as NOT exercised by any agent-run verification — no real network download was performed, since an unattended agent pass lacked explicit user permission to download. Code path is real and compiles but unexercised, not fabricated-and-claimed-working. No shared `:core` module with the phone's version.
- **Source**: `wear/.../engine/DownloadManager.kt:1-119`.

### FoldPostureProvider + FoldPosture/FoldState — app
- **Library/version**: `androidx.window:window` (Jetpack WindowManager) — `WindowInfoTracker`/`FoldingFeature`/`WindowLayoutInfo`; androidx Kotlin coroutines Flow.
- **Real capacity**: 5-value `FoldPosture` enum: `CLOSED_COVER` (never actually produced by this class — placeholder for a future cover-launch detector), `BOOK_PORTRAIT_FLAT`, `BOOK_PORTRAIT_ANGLED`, `TABLETOP_LANDSCAPE_FLAT`, `TABLETOP_LANDSCAPE_ANGLED`, `NO_FOLDING_FEATURE`. `postureFlow()` emits distinct-until-changed based purely on `FoldingFeature.orientation`/`.state` — never raw screen dimensions.
- **How it works**: `classify()` maps HORIZONTAL orientation to `TABLETOP_LANDSCAPE_FLAT`/`ANGLED` (by `state`) and VERTICAL to `BOOK_PORTRAIT_FLAT`/`ANGLED`; no feature at all → `NO_FOLDING_FEATURE`. `isMirroredTabletop` is true for either tabletop value. `hingeAngleFlow()` wraps `HingeAngleSensor` as pure progressive-enhancement — emits nothing on devices/API levels lacking the sensor; a collector must never depend on it for correctness.
- **Known limits/gaps**: A real, documented quirk on real Fold 5 hardware (RFCW80CK2RW): at FLAT (180°), `isSeparating` reports FALSE with a zero-height `bounds` rect (no physical step exists at that angle), so a literal `isSeparating` gate (the spec's original wording) would silently drop the FLAT half of the tabletop pairing the spec requires. The code deliberately classifies both FLAT and HALF_OPENED HORIZONTAL states identically by orientation alone, overriding the spec's literal wording in favor of its stated intent, explained inline. `CLOSED_COVER` is structurally unreachable via this class — `WindowInfoTracker` cannot observe a fully-closed device.
- **Source**: `app/.../fold/FoldPostureProvider.kt:1-115`, `FoldPosture.kt:1-67`; `fold5-adaptation.md` §2 (46-59,78-96).

### HingeAngleSensor — app
- **Library/version**: `android.hardware.Sensor`/`SensorManager`/`SensorEventListener` — `Sensor.TYPE_HINGE_ANGLE`, API 30+ only.
- **Real capacity**: Optional continuous 0-360° hinge-angle reporting, gated behind `Build.VERSION.SDK_INT >= R` before attempting `getDefaultSensor` — below R, the sensor field is unconditionally null and `isAvailable` false. `start()` returns false (no-op) when no sensor exists.

Confirmed present on the real Fold 5 via `adb shell dumpsys sensorservice` ("hinge_angle Wakeup | Samsung | type: android.sensor.hinge_angle(36)") — this device takes the live-sensor path.
- **Known limits/gaps**: Purely progressive-enhancement/animation-smoothing — core posture detection must never depend on it. No angle-to-layout interpolation logic lives in this class; it's only the raw-degrees source.
- **Source**: `app/.../fold/HingeAngleSensor.kt:1-86`; `fold5-adaptation.md` §2 (line 65).

### ContinuousListeningService (phone) — app
- **Library/version**: Plain `android.app.Service`, `android.os.PowerManager` (`PARTIAL_WAKE_LOCK`), `androidx.core.app.NotificationCompat` — no third-party library.
- **Real capacity**: One `PARTIAL_WAKE_LOCK` (tag `RetroidTranslator:ContinuousListening`, non-reference-counted, 2-hour safety-net ceiling — `MAX_WAKE_LOCK_DURATION_MS = 7,200,000ms`) plus `FOREGROUND_SERVICE_TYPE_MICROPHONE` (API29+; plain 2-arg `startForeground` on API 28) with a persistent low-importance notification. **Not** `START_STICKY** — deliberately will not auto-restart if killed.

### ContinuousListeningService (wear) — wear
- **Library/version**: Same primitives as the phone, no shared code — a separate, hand-written class.
- **Real capacity**: Ports the CONCEPT, not the code, with deliberate differences: no SDK-version gating anywhere (minSdk 30 already exceeds every gate the phone's minSdk 28 needed); notification carries `setLocalOnly(true)`; wake-lock ceiling is **30 minutes** (`30*60*1000L`), not the phone's 2 hours, given a 425mAh Watch6 Classic battery; no shared Application-level `MicPipeline` reference — a static `@Volatile onTaskRemovedListener` closure instead.

Disclosed gaps: `onTaskRemoved`'s swipe path code-reviewed only; only French→Spanish exercised (only two models downloaded); 30-minute ceiling and notification-bridging never verified against a paired phone (no verified pairing relationship exists).

### BulkDownloadCoordinator — app
- **Library/version**: No external library — pure Kotlin orchestration over `DownloadManager`/`TranslationEngine`/`VoskEngine`/`PiperTtsEngine`.
- **Real capacity**: Sequential (not parallel) downloader over all **92** downloadable packs (59 ML Kit translation + 25 Vosk STT + 8 Piper natural-voice), confirmed both by catalog grep and a real on-device summary card reading "X of 92 packs downloaded." Cancellation is cooperative, not preemptive — `cancel()` sets a volatile flag checked only between items, so an in-flight HTTP download finishes normally before the batch stops (a disclosed, deliberate limitation).
- **How it works**: `start(items, listener)` recurses through `downloadNext` (plain callback recursion, not a coroutine/loop): checks cancelled/exhausted, fires `onProgress`, calls `downloadSingle`, recurses with updated counts. `downloadSingle` is a public `when` dispatch keyed on `PackDescriptor`'s sealed subtype — `Translation`→`TranslationEngine.downloadModel`, `VoiceInput`→`DownloadManager.downloadAndUnzip`, `NaturalVoice`→`piper.downloadVoice` — reused identically by both the bulk flow and each pack row's individual Download button, one dispatch path for all single-pack downloads.
- **Known limits/gaps**: Progress percent is meaningful only for VoiceInput/NaturalVoice (real byte-level percent); always 0 for Translation packs (ML Kit's own API exposes no byte-level progress). Real end-to-end bulk run was deliberately never completed: progress observed advancing pack 1 of 83 to pack 9 of 83 over real Wi-Fi, then cancelled per the task's own "no need to run the full ~5GB download" instruction — cancel behaved correctly ("Cancelled. 11 downloaded, 0 failed before stopping"). 21 of 25 Vosk packs and 6 of 8 Piper voices never individually download-tested.

### LearnCourseLoader / LearnModels (course content model + loader) — app
- **Library/version**: None — plain `org.json.JSONObject` parsing of a bundled asset, no Room/Moshi/Gson.
- **Real capacity**: Exactly 1 language shipped (English, `"en"`), 2 units ("greetings", "numbers"), 1 lesson per unit (2 lessons: "greetings_1", "numbers_1"), 8 exercises per lesson (**16 total** across the course) — 2 of each of the 4 exercise types (MULTIPLE_CHOICE, WORD_BANK, LISTENING, SPEAKING) per lesson, confirmed by direct count of `app/src/main/assets/learn/en_course.json`. No de/es/fr course file exists anywhere in the repo, matching README's "Not yet built" note. `LearnFragment.loadCourse()` hardcodes preference for `"en"` — the Learn tab is not driven by the Translate tab's source/target selection at all.
- **How it works**: `LearnCourseLoader.load(context, langCode)` opens `assets/learn/<langCode>_course.json`, parses an in-memory `LearnCourse(language, units: List<LearnUnit>)` tree, caches the parsed result (or a cached "no course" miss) per langCode in a static `HashMap`. `availableCourseCodes()` lists `assets/learn/*_course.json` and strips the suffix. `LearnExercise.key(lessonId, index)` produces the stable `"<lessonId>#<index>"` string used in SQLite `exercise_key`. `LearnCourse.resolveExerciseKey()` reverses that key (via `substringAfterLast('#')`/`substringBeforeLast('#')`, deliberately not `split("#")`, so a lesson id containing a literal `#` wouldn't break it) back into a `ResolvedExercise` for the review-queue cover-screen variants that jump straight into a due item. Content is pre-authored, bundled at build time — nothing is fetched or generated at runtime; adding a language means manually authoring a new `<langCode>_course.json` in the same schema.
- **Known limits/gaps**: README's self-reported "not yet built": Spanish/German/French course content (schema pipeline supports it, nothing authored/verified), and a dedicated review-queue UI (note: `progress_ring`/`course_dashboard` cover variants now do read `LearnReviewQueue`, a later addition than README's own scope description). No versioning/migration story for course JSON — a renamed lesson id orphans previously-recorded `srs_state`/`lesson_completion` rows (silently dropped via `resolveExerciseKey` returning null, filtered via `mapNotNull`).
- **Source**: `app/.../learn/LearnModels.kt:1-125`; `app/.../assets/learn/en_course.json:1-47`; `app/.../ui/LearnFragment.kt:192-196`; `README.md:20,28-32,71`.

### LearnProgressStore (SQLite-backed XP / streak / lesson-completion / SRS state) — app
- **Library/version**: `android.database.sqlite.SQLiteOpenHelper` (built-in, no Room) — `DB_NAME="learn_progress.db"`, `DB_VERSION=1` (no migrations shipped; `onUpgrade` drops and recreates all 3 tables).
- **Real capacity**: 3 tables: `app_state` (key/value: `xp_total`, `streak_count`, `last_active_date` — only 3 keys ever written), `lesson_completion` (`lesson_key TEXT PRIMARY KEY, completed_at_epoch_ms, xp_earned`), `srs_state` (`exercise_key TEXT PRIMARY KEY, box, next_review_epoch_day, correct_count, incorrect_count`). Single lazily-constructed instance shared app-wide via `TranslatorApp.learnProgress by lazy {...}` — every Learn UI variant reads/writes the same store. XP economy (from `LearnFragment`, not the store): **+10 XP per correct answer**, batched at lesson-end in normal flow, posted immediately per correct answer in the review queue. Displayed "level" is a pure UI derivation, not a stored field: `totalXp() / 100 + 1` (`LearnFragment.kt:1007`).
- **How it works**: Streak: `recordActivityToday()` compares today's date against stored `last_active_date` — same day leaves streak unchanged (floored at 1); exactly yesterday increments by 1; a 2+ day gap or first-ever activity resets to 1. Idempotent for same-day calls. Lesson completion: `recordLessonCompleted()` is an upsert (`CONFLICT_REPLACE`) — re-completing overwrites rather than duplicates. Due-review queries (`dueExerciseKeys`, `dueCountsByBox`) are plain read-only SELECTs over `srs_state` filtered by `next_review_epoch_day <= today`.
- **Known limits/gaps**: No account/cloud sync (local-only by design). No XP decay, no streak-freeze/grace mechanic — missing a day always resets to 1. `app_state` has no schema versioning beyond the whole-DB `DB_VERSION`. `srs_state` rows persist forever even if the referencing exercise is later removed from course JSON.
- **Source**: `app/.../learn/LearnProgressStore.kt:1-222` (schema 24-51, streak 78-90, completion 98-111, due-query 156-195); `TranslatorApp.kt:27`; `LearnFragment.kt:458-492,1007`.

### Leitner-box spaced repetition (LearnProgressStore.recordAnswer + LearnReviewQueue) — app
- **Library/version**: Custom implementation, no external SRS library (not Anki-style SM-2, not a third-party dependency) — same `LearnProgressStore` plus a small standalone `LearnReviewQueue` object.
- **Real capacity**: Exactly **5 boxes**, indices 0..4, hardcoded interval schedule in days: `boxIntervalDays = intArrayOf(0, 1, 2, 4, 7)` — box 0 due same day, box 4 max 7-day gap. One `srs_state` row per exercise key (up to 16 possible rows for the current English course).
- **How it works**: `recordAnswer(exerciseKey, correct)` reads current `(box, correct_count, incorrect_count)` (defaulting to box 0/0/0 if never answered). On correct, `box = (box+1).coerceAtMost(4)`; on incorrect, `box` resets straight to **0** (not decremented). `next_review_epoch_day` recomputed every time and upserted. "Due" (`dueExerciseKeys()`) excludes exercises with no `srs_state` row at all (never-answered = "new," not "due"). `LearnReviewQueue.dueNow()` maps due keys back through `resolveExerciseKey()`, silently dropping unresolvable keys; `boxCounts()` returns `(box, dueCount)` pairs for all 5 boxes, rendered by the `course_dashboard` cover-screen panel.
- **Known limits/gaps**: A simplified Leitner variant, not full SM-2/Anki scheduling — no per-item ease factor, no randomized jitter, no partial-credit distinction between "barely wrong" and "completely wrong" (any incorrect answer fully resets to box 0). Progression is linear and capped at box 4 — no exponential growth, no terminal "mastered" state.
- **Source**: `app/.../learn/LearnProgressStore.kt:114-195` (boxIntervalDays 117, recordAnswer 119-145, dueExerciseKeys 176-186, dueCountsByBox 189-195); `app/.../learn/LearnReviewQueue.kt:1-32`.

### AnswerChecker (Speaking-exercise lenient word-overlap scoring) — app
- **Library/version**: None — pure Kotlin string/regex normalization, no ML/NLP library; feeds off the same `VoskEngine`/`MicPipeline` transcript the Practice tab uses.
- **Real capacity**: Default match threshold **0.6** (60% of expected words must appear in the transcript). Order-independent, punctuation/case-insensitive.
- **How it works**: `normalize(text)` lowercases, strips non-alphanumeric/non-space characters, splits on whitespace. `matches(expected, transcript, threshold=0.6)` turns the transcript's words into a `Set` (dedup, order-independent), counts how many of the expected phrase's words appear, returns true if `hits / expectedWords.size >= threshold`. `overlapRatio()` exposes the same fraction directly (used for UI, e.g. "73% match"). Explicitly NOT phonetic/pronunciation scoring, mirroring Practice's "listen-and-compare, not a grader" boundary.
- **Known limits/gaps**: Word-order is completely ignored; transcript dedup via `.toSet()` means each expected word counts once regardless of repeats. No phonetic distance/fuzzy matching (e.g. Levenshtein) — a mis-transcribed homophone or Vosk STT error counts as that word simply missing.
- **Source**: `app/.../learn/AnswerChecker.kt:1-40`; `LearnFragment.kt:751-752,1484`.

### Content sourcing & licensing (Tatoeba attribution) — app
- **Library/version**: N/A — static bundled JSON content, not a runtime library.
- **Real capacity**: All 16 shipped exercise sentences are real Tatoeba Project sentences (not synthetic/LLM-generated), each carrying its permanent Tatoeba sentence ID (spot-checked: tatoebaId 2258234 = "Good morning.", 1037732 = "My very educated mother just showed us nine planets."). Multiple-choice `gloss` text (4 of 16 exercises) was authored specifically for this app — explicitly NOT Tatoeba-sourced, per both the JSON's `sourceNote` field and README's license table.
- **How it works**: License: CC-BY 2.0 FR, per `en_course.json`'s top-level `sourceNote` string and README's Learn-tab license-table entry, verbatim-consistent. `sourceNote` ships inside the app's own asset, not just doc-only. A separate vocabulary-frequency dataset (`hermitdave/FrequencyWords`, MIT) is named in README as an *intended* future prioritization source but README itself states it "has not yet been integrated into any shipped course content" — confirmed: zero references anywhere in Learn source files or `assets/learn/`.
- **Known limits/gaps**: Only English content exists, so CC-BY 2.0 FR attribution currently applies to one course file. No per-sentence attribution renders in the app UI itself (lives in the JSON `sourceNote` field and README only) — grepped `LearnFragment.kt` for any UI rendering of `tatoebaId`/`sourceNote`, found none; `tatoebaId` is stored on every exercise but only ever used as opaque content.
- **Source**: `app/.../assets/learn/en_course.json:3`; `README.md:30,71`; `app/.../learn/LearnModels.kt:6-13`.

**Real gap found and fixed while building this**: on this project's AGP 8.3.2 setup, calling into `org.json.JSONObject` from a plain `src/test` unit test does not throw ("not mocked") the way Android's stub-jar unit-test docs describe — it silently succeeds and returns default/empty values (blank strings, `0`, `null`) with no exception at all, which is a worse failure mode than a crash (a parsing test would pass-but-lie, asserting on values `optString`/`optJSONArray` never actually produced). Everything above is plain-JVM-testable pure logic only. Not covered: `TranslationEngine`, `VoskEngine`, `MicPipeline`, `TtsRouter`, any `Fragment`/`Activity`/UI code, `LearnProgressStore` (SQLite, needs a real or Robolectric-provided `SQLiteOpenHelper`), and `AnswerChecker` (untested this pass despite being pure logic — not one of the audit's named first targets, left for a follow-up).
