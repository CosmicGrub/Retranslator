# Engine upgrade plan: scoped opportunities across all five engines

Companion to `engines-inventory.md` — that doc catalogs what's built and its current capacity; this one scopes what could change, for each engine, verified against live upstream sources (Maven metadata, GitHub release/changelog history, model cards, official compatibility docs) rather than assumed. Compiled 2026-08-16. Every effort/risk estimate below is grounded in a specific citation, not a guess — where something turned out to be easier or harder than it looked at first glance, that's called out explicitly.

Organized by how ready each item is to act on, not by engine — the point is knowing what to actually do first.

## Tier 2 — small, mechanical, roughly half a day each

~~**Re-vendor sherpa-onnx v1.13.4 → v1.13.5.**~~ **DONE (`fold5-quality-tier1-2` branch, 2026-08-18)** Confirmed real (released 2026-08-11, currently the latest tag — checked the releases page directly, no newer since). The Kotlin `OfflineTts.generate(text, sid, speed)` signature this app actually calls is unchanged per both the changelog and upstream source, so no `PiperTtsEngine.kt` code changes needed — purely a re-extract-and-swap of `libs/sherpa-onnx-classes.jar` + the four `jniLibs/arm64-v8a/*.so` files, exactly mirroring how this project already vendored 1.13.4. What's actually in it that matters here: **"Fix use-after-free in async TTS progress callbacks (#3781)"** (real memory-safety fix) and **"fix(tts): insert pad after BOS in PiperPhonemesToIdsVits"** — a correctness fix specifically in the Piper VITS phoneme pipeline this app's code drives directly, not an unrelated part of the library. Because that second fix touches the exact synthesis path, a full 4-language regression pass (not just a smoke test) is warranted after the swap. **Real evidence**: re-vendored, API/JNI-symbol-compatibility-checked, and real-device-regression-tested on `RFCW80CK2RW` — see `docs/evidence/fold5-edition/sherpa-onnx-1.13.5-regression.md`, including an honestly-disclosed gap (2 of 4 languages' synth confirmation interrupted by a real, repeated shared-device collision with a sibling agent's build, then the device itself dropping off `adb` entirely).

**Add Japanese/Korean/Devanagari OCR script packs.** Confirmed all three cap at the same `16.0.1` version as the Chinese pack already in use, via the same `dl.google.com` group-index fetch used to verify Chinese. Exact coordinates ready to use without re-deriving:

| Script | Coordinate | Recognizer class |
|---|---|---|
| Japanese | `com.google.android.gms:play-services-mlkit-text-recognition-japanese:16.0.1` | `com.google.mlkit.vision.text.japanese.JapaneseTextRecognizerOptions` |
| Korean | `com.google.android.gms:play-services-mlkit-text-recognition-korean:16.0.1` | `com.google.mlkit.vision.text.korean.KoreanTextRecognizerOptions` |
| Devanagari | `com.google.android.gms:play-services-mlkit-text-recognition-devanagari:16.0.1` | `com.google.mlkit.vision.text.devanagari.DevanagariTextRecognizerOptions` |

The code pattern is genuinely mechanical (`isScriptReady`/`downloadScript` already generalize via `ModuleInstallClient` with zero script-specific logic) — 3 dependency lines, 3 `OcrScript` enum entries, 3 `when`-branches. Two real gotchas for whoever picks this up: **the Japanese verification sample must mix in kana, not just kanji** (a kanji-only string is ambiguous with the Chinese recognizer, since they share Han characters), and **Devanagari is a script, not a language** — the recognizer covers Hindi/Marathi/Nepali/Sanskrit alike, but `TranslationEngine.translate()` downstream needs one concrete language code; Hindi (`"hi"`) is the natural pick since it's already in the Vosk catalog.

**Extend `TestAudioSynth` to all 25 Vosk catalog languages.** Currently only English and Spanish have any accuracy measurement in this codebase at all. The harness already drives eSpeak-ng's `SpeechSynthesis` JNI class directly, and eSpeak already ships ~114 languages bundled in-APK — a strict superset of Vosk's 25, so no new TTS dependency is needed to generate test audio. Extending `PHRASES` from 6 entries (2 languages) to ~75 (25 × 3 phrases) is mechanical; the only per-language unknowns are confirming `EspeakLanguageMap.toEspeakLanguage()` covers each of the 25 codes, and authoring 3 real (non-word-salad) sentences per language. This turns "22 of 25 never decode-tested" into "22 of 25 sanity-tested" without touching real-device time or licensing.

~~**Add 1–2 new-language Piper voices to the existing 4-language set.**~~ **Italian pilot DONE (`fold5-quality-tier1-2` branch, 2026-08-18)** Piper's actual upstream catalog (now maintained at `OHF-Voice/piper1-gpl`, the post-relicense successor to the archived `rhasspy/piper`) covers roughly 35–51 languages total, and sherpa-onnx's own hosted `tts-models` release — the exact source this project already downloads from — is described upstream as covering "more than 40 languages." ## Tier 3 — real engineering, worth its own scoped pass

**Piper language expansion beyond the pilot above.** 18 of the 25 Vosk catalog languages have a Piper voice available upstream (`ar, ca, cs, fa, hi, it, ja, kk, ko, nl, pl, pt, ru, sv, te, tr, uk, vi`) that this app doesn't use yet — real, sizeable value (most of what Vosk/ML Kit already support could get a natural-voice option), but each needs its own model-card license check before adding (only Italian is confirmed clean so far; the rest are unverified, not confirmed-bad — genuinely unchecked). One caveat already surfaced: M-AILABS' Ukrainian audio specifically is licensed narrower ("machine learning purposes only") even though the rest of that dataset is public domain, so don't assume language-level uniformity within a single upstream dataset. One unverified candidate flagged but explicitly **not** ready — a Japanese voice (`hi_fi_captain`) added to the Hugging Face mirror "1 day" before this audit, whose license couldn't be confirmed because the source corpus page was down.

**eSpeak's 16KB-alignment fix — corrected framing: this is not actually blocked.** The original 16KB audit (this session, earlier) concluded there was no fix path short of a from-scratch native build. That undersold it: espeak-ng's own upstream repo already has a working Android build module (`android/` — its own `build.gradle` + `jni/CMakeLists.txt`, CMake 3.22.1). The actual root cause of the misalignment is that this module is pinned to **NDK r26** (`ndkVersion "26.1.10909125"`), and 16KB alignment only became NDK's *default* output starting at **r28** — r27 and earlier need explicit `-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384` linker flags to get it at all, which r26's config has neither of. So the realistic path is: bump that module's NDK pin (or add the linker flags), rebuild `ttsespeak` for arm64-v8a, verify alignment with `readelf`, re-vendor `libttsespeak.so` + `espeak-ng-data` the same way this project already vendors sherpa-onnx. Real risk isn't the build logic — it's that **this project has never done a native rebuild of anything before**, so first-time NDK/CMake toolchain setup is the actual unknown, plus the vendored `com.reecedunn.espeak.*` Java classes carry no version-pin comment, so their JNI-surface compatibility against current espeak-ng (1.52.0, Dec 2024 — also confirmed the newest release, also confirmed to have shipped no 16KB fix of its own) should be checked before rebuilding against a different tag. Bracket this as half a day in the best case, genuinely multi-day if new NDK/Clang toolchain warnings-as-errors surface in eSpeak's older C code.

**Device-tiered Vosk resident-model cap.** The one-model-at-a-time design was written for the original Retroid Pocket 2+ target (~1GB usable RAM). Real measured numbers show this constraint doesn't apply uniformly across today's device fleet: Fold5 has 11.4GB total RAM with ~3.7GB `MemAvailable` even with 2 models loaded; Tab S9 FE has 6GB total. Both have 15–20× the headroom a 3rd concurrent small model (~107MB average delta, per the existing 2-model measurement) would cost. **Watch6 Classic is the opposite case** — only ~426MB real `MemAvailable` (not its 1.8GB nominal total; Samsung's OEM stack consumes most of it), with 77MB idle app PSS already, putting it closer to the original Pocket 2+ design point than either phone target. The dual-recognizer pattern (`ContinuousConversationController`) already proves N-instance generalization is mechanically easy (two fully independent `VoskEngine` objects, no shared state) — decode wall-time was measured at 1.9× for 2 concurrent recognizers (sub-linear, not naive 2×); a 3rd would plausibly land ~2.6–2.9× by the same trend, though that's extrapolation, not a measurement. Recommendation: pre-warm a 3rd language on Fold5/Tab-class hardware specifically, leave Pocket 2+ and Watch6 (which doesn't even use the dual-recognizer pattern today — it's wired single-recognizer only) at one resident model.

**English Vosk `lgraph` model as an opt-in accuracy tier.** Pulled the full upstream `model-list.json` (131 entries) plus WER/CER table directly. English has a real, cheap middle tier the current catalog skips entirely: `vosk-model-en-us-0.22-lgraph`, 124.5MiB, WER 7.82/8.20 vs. the current small model's 9.85/10.38 — roughly a 20% relative accuracy improvement for ~3× the download, not the ~46× the full "big" model (1.8GiB, WER 5.69/6.05) would cost. This is the one clearly cheap, clearly clean-licensed upgrade candidate in the whole 25-language catalog — most other languages' "big" tiers cost 700MB–1.9GB for a real but much more expensive gain, and two candidates are outright license-blocked (Portuguese's big model is GPLv3.0 — the same license-conflict class already flagged for eSpeak in this repo; Dutch's is CC-BY-NC-SA, non-commercial). One that looked good on paper but isn't safe to adopt: Arabic's `vosk-model-ar-mgb2-0.4` scores far better than the current pick (WER 16.40 vs. 28.50, Apache-2.0, 1/4 the size) but is flagged `obsolete: true` upstream — real hosting-continuity risk. Recommend piloting English's lgraph tier alone first (cheap, unambiguous) before deciding whether the catalog/UI/download-plumbing work is worth repeating for the more expensive tiers elsewhere.

## Tier 4 — large and strategic; do not fold into an unrelated feature pass

**compileSdk 34→35 + AGP 8.3.2→8.6.1+** (the prerequisite for CameraX 1.5.1, and separately relevant now that Google Play's 16KB-page-size enforcement deadline has passed) is **not a contained afternoon** — this was the original 16KB audit's framing, and it undersold the real cascade:

- compileSdk 35 requires AGP 8.6.1+ (Android's own "Set up the Android 15 SDK" guidance).
- AGP 8.6.0+ requires Gradle 8.7 minimum — already satisfied, no wrapper bump needed there.
- **The real blocker**: Kotlin's own official AGP-compatibility table caps Kotlin 1.9 (currently pinned: 1.9.22) at AGP 8.2, and Kotlin 2.0 at AGP 8.3 — neither reaches 8.6.1. Getting to AGP 8.6+ forces a **Kotlin 1.9→2.1+ jump** (current stable is 2.4.0 as of this audit), which defaults to the **K2 compiler** — a different front-end, real risk of new compile errors or behavior changes across the *entire* codebase, not just the OCR code that motivated this — and moves the Compose compiler out of `composeOptions.kotlinCompilerExtensionVersion` into a separate Gradle plugin, a real rewire for `:wear` specifically (its `build.gradle.kts` already carries a comment acknowledging this exact fork in the road).
- **Strategic recommendation**: bump compileSdk only, leave `targetSdk` at 34. CameraX 1.5.x's release notes only require compileSdk, not targetSdk — and since eSpeak's 16KB alignment issue has no fix yet (Tier 3 above), bumping targetSdk to 35 alongside this would convert that from a disclosed-but-latent issue into a **hard Google Play submission blocker**, since Play's enforcement specifically triggers on apps *targeting* API 35+.

Bracket as a genuine multi-day migration (AGP bump + forced Kotlin jump + K2 fallout across both modules + Compose-compiler-plugin rewire for `:wear` + full regression pass on real Fold 5 and Watch6 hardware + re-attempting the previously-failed CameraX 1.5.1 build to confirm it now succeeds), medium-high risk concentrated in the K1→K2 compiler switch, not the version numbers themselves.

## Blocked on a human, not on engineering

- **Watch6 Classic Vosk verification.** The hard technical unknown is already resolved favorably — `VoskEngine.probeNativeLoad()` confirms the native stack loads cleanly on the real 32-bit ABI across 3 install cycles, a catchable exception rather than a crash. What's left is downloading real English (~39MB) + Spanish (~38MB) models and running them through the already-wired single-recognizer flow. This is explicitly gated on the user's direct, own-words permission for the download — correctly not proceeded on even when a message *appeared* to authorize it mid-task in a prior pass, per this project's own established rule that only the human user's direct words count as consent for a gated download.
- **A real photographed-text OCR test.** No agent can hold a device up to a printed sign or book. Structurally identical to the already-disclosed "no live human speaker" gap for STT — a hardware/human-availability constraint, not a code deficiency.

## Also surfaced, opportunistic only

- **JNA 5.18.1 → 5.19.1**: confirmed a newer version exists, but low value here specifically — 5.19.0 introduced a real Android regression (silently raising the effective minSdk to 26 via `MethodHandle` usage D8 can't desugar below that), fixed in 5.19.1, but this app's actual `minSdk` (28 phone / 30 wear) already clears that regression either way. Safe to bundle with any other engine touch, not worth a dedicated pass.
- **In-app disclosure for upstream-known-poor languages.** Telugu's own upstream WER is 87.9 (Fleurs benchmark) — not a testing gap, a disclosed near-unusable number with no bigger fallback model available. Several other catalog languages have no upstream WER figure published at all. Worth surfacing this honestly in the language picker rather than presenting all 25 as equivalent.
- **Unused sherpa-onnx TTS capabilities**: `OfflineTts.generateWithCallback(...)` (streaming synthesis — lets playback start before the whole utterance finishes synthesizing; `PiperTtsEngine` currently only calls the blocking `generate(...)`, a limitation its own code comment already acknowledges) and newer non-Piper model architectures (Kokoro 1.0, KittenTTS, MatchaTTS) that landed in sherpa-onnx alongside Piper support — the latter are alternatives to Piper, not upgrades to it, and would mean a new voice catalog and different quality/size/speed tradeoffs; speculative future work, not a near-term item.
- **Vosk's own upstream traceability gap**: versions 0.3.70 and 0.3.75 have no corresponding GitHub tag or Release (last tagged release is v0.3.50, April 2024) — the actual changes were traced via raw commit history instead. Not something to fix, just worth knowing when debugging a future Vosk-related issue.
